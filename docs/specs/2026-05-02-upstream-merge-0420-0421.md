## 1. Objective

Cherry-pick upstream commits from tags `0.4.20`, `0.4.21`, and commit `796dbd4` onto the `update` branch, **excluding** commit `82ccf6645df62a7c6` ("Record worktree parent at creation so /worktree finish picks the right merge target").

### Rationale for Exclusion

Commit `82ccf66` introduces a `claudechic-parent-branch` file stored in `.git` to record worktree parentage at creation time, providing an implicit default for `/worktree finish`. Our `0.4.19.9` branch implements parametrized base-branch support via explicit `get_finish_info(base_branch=...)` with an 8-level validation chain.

**Are these complementary or competing?** They serve adjacent but overlapping purposes:
- Upstream's file: "which branch did I come from?" (implicit, used when user doesn't specify)
- Our parameter: "which branch should I target?" (explicit override at finish time)

The approaches are potentially complementary (file provides default, parameter provides override). However, both modify `get_finish_info()` and the FinishInfo dataclass — our version already has `needs_checkout` and frozen semantics that conflict with 82ccf66's additions. Reconciliation requires careful merging of:
- FinishInfo field sets (our `needs_checkout` vs their `recorded_parent`)
- Validation ordering (our 8-step chain vs their file-read + heuristic fallback)
- The `commands.py` creation path (their write at create time, our validation at finish time)

**Decision:** Exclude now; reconcile in a dedicated follow-up within 2 weeks (before 0.4.22). The complementary design is the target end state.

## 3. Conflict Analysis

### Understanding the Conflict Mechanics

These are **context conflicts from cherry-pick**, not "upstream deletions." The topology is:

```
a6624cf (shared merge-base)
   |
   +-- [6 upstream commits] --> 796dbd4 (upstream/main)
   |
   +-- [186 fork commits] --> e3c81ac (our HEAD)
```

When cherry-picking `1bd8667`, git computes `diff(a6624cf, 1bd8667)` and applies it to `e3c81ac`. Our 186 commits have moved lines, added imports, and restructured functions — meaning the patch's context lines won't match. This produces context conflicts (line drift), not semantic disagreements. Resolution requires understanding both sides' intent.

**Note:** Upstream never had our `notify()` override, `strip_ansi`, or context tracking. The "conflict" is that upstream's patches expect the old code shape. We are not "rejecting upstream's removal" — we are resolving context drift where upstream's patch targets code we've since modified.

## 4. Integration Strategy

### 4.1 Approach: Sequential Cherry-Pick with Dry-Run Validation

**Why not rebase:** Our branch has 186 commits with merge commits; interactive rebase would be destructive and error-prone.

**Why not merge:** A direct `git merge upstream/main` would bring in `82ccf66` which we're excluding. Alternative "merge + revert" was considered but rejected: `82ccf66` touches the same files as our parametrized-finish feature, making the revert itself conflict-prone.

**Why not rebase our 4 `update` commits onto upstream:** The `update` branch is based on `main` (which has the full 186-commit divergence). Rebasing just the 4 update commits would require rebasing all 186.

**Procedure:**

1. **Dry-run first** — validate actual conflicts before committing to the approach:
   ```bash
   git checkout -b merge-upstream-dry-run update
   for sha in b6a16b6 1bd8667 d46b3af e0cea68 15f4e81 796dbd4; do
     echo "=== Cherry-picking $sha ==="
     git cherry-pick --no-commit $sha 2>&1 || { git cherry-pick --abort; echo "CONFLICT at $sha"; }
     git reset --hard HEAD
   done
   git checkout update
   git branch -D merge-upstream-dry-run
   ```
   Document actual conflicts. Abort if conflicts are worse than predicted.

2. Create integration branch from current `update` HEAD:
   ```bash
   git checkout -b merge-upstream-0420-0421 update
   ```

3. Cherry-pick in dependency order, tagging after each success:
   ```bash
   # SDK bump first (our >=0.1.55 already satisfies, but pyproject.toml needs resolution)
   git cherry-pick b6a16b6
   git tag checkpoint/after-sdk-bump

   # Permission mode feature (largest, most conflicting)
   git cherry-pick 1bd8667
   git tag checkpoint/after-permission-mode

   # Diff viewer fixes (independent, clean applies)
   git cherry-pick d46b3af
   git cherry-pick e0cea68
   git tag checkpoint/after-diff-fixes

   # SSH color warning (additive)
   git cherry-pick 15f4e81
   git tag checkpoint/after-ssh-warning

   # Special-char crash fix (conflicts with our _sanitize_id)
   git cherry-pick 796dbd4
   git tag checkpoint/after-sanitize-id
   ```

4. Resolve conflicts per Section 3.1 resolution strategies.

5. Run verification:
   ```bash
   uv run python -m pytest tests/ -n auto -q
   uv run pre-commit run --all-files
   ```

### 4.2 Conflict Resolution Principles

1. **Our features are retained:** `notify()` override, `strip_ansi()`, context tracking, `_prepare_prompt()`, `TOKEN_REMINDER_PATTERN`, `_width` — all stay. These are features upstream doesn't have; conflicts arise from context drift, not design disagreement.
2. **Our context tracking is non-negotiable:** `_prepare_prompt()`, `update_context()`, `TOKEN_REMINDER_PATTERN` stay.
3. **Upstream's permission mode is additive:** It adds a new mode without removing our features. Accept fully, then wire into our existing infrastructure.
4. **Upstream's diff fixes take precedence:** Their `_sanitize_id` regex approach and tab/syntax fixes apply cleanly to files we haven't touched.
5. **SDK version:** Keep our higher floor (`>=0.1.55`) since it's a superset of `>=0.1.36`.
6. **Cherry-picked tests require validation:** Tests from upstream were written for a simpler codebase. After cherry-pick, verify imports resolve, fixtures exist, and assertions match our state.

### 4.4 "Auto" Mode Semantics

For clarity, here's the mode state table after integration:

| Mode | SDK Value | UI Label | Footer Class | In Shift+Tab Cycle | Tool Approval Behavior |
|------|-----------|----------|--------------|---------------------|----------------------|
| `default` | `"default"` | "Auto-edit: off" | (none) | Yes | Prompt for all |
| `acceptEdits` | `"acceptEdits"` | "Auto-edit: on" | `accept-edits` | Yes | Auto-approve edits, prompt for others |
| `plan` | `"plan"` | "Plan" | `plan-mode` | Yes | Read-only, no tool execution |
| `auto` | `"auto"` | "Auto" | `auto-mode` | Yes | Auto-approve all (classifier-based) |
| `planSwarm` | `"plan"` | "Plan" | `plan-mode` | No (internal) | SDK plan mode, triggered by /planswarm |

**Security note on "auto":** This delegates tool approval to the SDK's built-in classifier (same as Claude Code CLI's `auto` mode). It does NOT blindly approve — the SDK has its own safety layer. Our `can_use_tool` should return `PermissionResultAllow` without prompting the user, letting the SDK's internal classifier decide.

## 8. Sustainability & Future Strategy

### The Cherry-Pick Debt Problem

Cherry-picking creates duplicate commits with different SHAs. Git cannot track that `b6a16b6` (upstream) and our cherry-picked copy are the same change. Future `git merge upstream/main` will attempt to re-apply them, causing false conflicts.

### Mitigation

1. **Track cherry-picked SHAs:** Create `CHERRY_PICKED.md` listing all integrated upstream SHAs with their fork-side equivalents.
2. **Evaluate strategy at next upstream release:** If 0.4.22 is small (1-3 commits, no worktree changes), continue cherry-picking. If 0.4.22 is large or touches worktree code, switch to "merge + revert 82ccf66" approach — by then we'll have completed the 82ccf66 reconciliation.
3. **82ccf66 reconciliation deadline:** 2 weeks (by 2026-05-16). Target design: upstream's file provides the default, our parameter provides the override. Integrate both into `get_finish_info()`.
4. **Long-term goal:** Reduce divergence to zero config-gatable features (via `features:` section in `.claudechic.yaml`) so full upstream merge becomes possible without exclusions.

### Decision Triggers for Strategy Change

| Condition | Action |
|-----------|--------|
| Upstream 0.4.22 touches `features/worktree/` | Reconcile 82ccf66 first, then merge |
| Cherry-pick conflicts take >2 hours | Switch to merge+revert for that release |
| 3+ consecutive cherry-pick cycles | Re-evaluate fork maintenance strategy |
| Upstream builds on 82ccf66's mechanism | Reconcile immediately |
